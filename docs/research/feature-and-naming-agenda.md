## 1. 为什么「命名」必须和「功能」一起调研

在这个产品里，**功能的名字就是用户对着麦克风说出的词**。命名因此不是品牌问题，而是**功能可用性问题**——说错了词，功能就等于不存在。

现状是**四层命名各说各话，且没有任何映射表**：

| 概念 | 代码标识符 | UI 文案 | 文档用词 | 用户可能说 |
|---|---|---|---|---|
| 待办实体 | `TodoItem` / `TodoRowVm` | 待办 | 待办 / 任务 / 事项 | 「记一下」「提醒我」「加一条」 |
| 计时 | `TimerItem` / `SchedItem` | 计时 / 定时器 | 计时 / 定时器 / 倒计时 | 「计时」「定个闹钟」 |
| 间歇结构 | `IntervalPhase` / `Phases` | 间歇训练 | 间歇 / HIIT / 计时组 | 「做八组」「间歇训练」「hit」 |
| 语音入口 | `VoicePipeline` | 「对我说…」 | 语音 / 会话 / 常驻 | 「你好…」？ |
| 运行记录 | `TimerSession` | **未定名** | 留痕 / 运行记录 | — |
| 免提场景 | `AppSettings.Scene` | 免提场景 | 场景 / 模式 | — |

> 证据：上表左右两列的差异可直接在 `voicetodo-master.md`（用「待办/计时/留痕」）与 `design-direction-v1.md`（用「任务/事项/计时器」）之间核对到。

**结论**：命名调研不是「以后再说」的美化工作，它是：
- 语音解析（P1-1）的**输入**；
- i18n 收口（P1-11）的**前提**；
- 领域模型重命名（P2-5）的**依据**。

## 2. 命名类调研（N）

### N1 · 产品名与品牌可用性

| 项 | 内容 |
|---|---|
| 要回答 | `VoiceTodo` 能不能作为**对外名**？还是只作工作代号？中文名是什么？ |
| 已存在的风险信号 | `market-and-competitors.md` 竞品表中**已有名为 “VoiceTodo” 的产品**（SpeakToDo / VoiceTodo 一栏）→ 重名风险是真实的，不是假想 |
| 方法 | ① 商标检索（中国商标网 / USPTO / EUIPO，第 9、42 类）；② 应用商店检索重名（App Store / Google Play / 微软商店）；③ 域名与社交账号可用性；④ 发音与记忆度测试（找 5~10 人复述）；⑤ 跨语言歧义（中/英/日） |
| 产出 | 候选名短名单（3~5 个）× 可用性矩阵（商标 / 商店 / 域名 / 发音 / 歧义） |
| 落点 | App 显示名、包名、商店页；仓库名与 `VoiceTodo.*` 工程名**是否跟着改**由本项结论决定 |
| 成本 | 中（商标检索需人工） |

### N2 · 术语表 Glossary（四层命名映射）

| 项 | 内容 |
|---|---|
| 要回答 | 每个核心概念，在代码 / 中英 UI / 文档 / 语音 四层分别该叫什么？ |
| 方法 | 以第 1 节那张表为骨架，逐条锁定，形成**五列映射**：概念 · 代码标识 · 中文 UI · 英文 UI · 语音触发词；对无争议项直接定稿，对争议项（Todo vs Task、Timer vs 定时器）列出理由后二选一 |
| 产出 | `docs/design/glossary.md`（单一事实来源） |
| 落点 | `Core/Resources/CoreStrings.cs`、`Services/CoreLocalizer.cs`、各 `*.xaml` 文案、领域模型命名 |
| 成本 | 低（半天）· **收益最高**：一次做对，避免 i18n 与解析器两头返工 |

### N3 · 语音触发词语料（Utterance Corpus）★

| 项 | 内容 |
|---|---|
| 要回答 | 用户实际用哪些词表达六类意图？哪些说法会撞车？ |
| 六类意图 | 新建待办 · 完成 · 删除 · 查询 · 建倒计时 · 建间歇 |
| 方法 | ① **自我日记法**（最便宜、最相关）：记录自己一周内「想对 App 说」的原话；② 小样本真人：微信问 5~10 人「你会怎么说」；③ 竞品 1~3 星评论挖掘（Todoist Ramble / Voice Timer 等）里的用户原话；④ 搜索联想词（百度 / Google / 小红书 / 知乎） |
| 要抓的冲突 | 「**开始**」→ 是开始计时还是开启会话？「**记一下**」→ 待办还是备忘？「**删掉它**」→ 指代谁（对应 X-4 会话状态）？「**闹钟**」→ 计时还是提醒？ |
| 产出 | 意图 → 正样本说法表 + **负样本表**（同音 / 多义 / 易误触词） |
| 落点 | `RuleBasedIntentParser` 关键词表、`VoiceCapturePage` 提示文案、`docs/models.md` 的识别示例 |
| 成本 | 低 · **决定核心卖点成败** |

### N4 · 领域模型与标识符命名审计

| 项 | 内容 |
|---|---|
| 要回答 | 现有类名是否表意准确？ |
| 已知可疑项 | `VoiceCommand` 实际承载的是「解析结果」而非「命令」；`Phases`（属性）与 `IntervalPhase`（类型）颗粒度不一致；`SchedItem` 是页面内部类型却承担核心概念；`TodoItem` 与 UI 的「待办/任务」未对齐 |
| 方法 | 逐类型过一遍 Core 的 `Models/` 与 `Abstractions/`，按「名字能否预测职责」判定 |
| 产出 | 重命名清单 + 影响面（引用数 / 迁移成本） |
| 落点 | `src/VoiceTodo.Core/**` |
| 成本 | 低（审计）/ 中（执行） |

### N5 · i18n 术语对照 与 商店关键词（ASO）

| 项 | 内容 |
|---|---|
| 要回答 | 中英双语的术语怎么对？商店里用户会搜什么？ |
| 方法 | ① 基于 N2 产出中英对照；② ASO：中文候选词（语音待办 / 离线提醒 / 免提计时）、英文候选词（voice todo / offline task / hands-free timer），看竞品在用什么词 |
| 产出 | 双语术语表 + 商店关键词候选（各 10~20 个） |
| 落点 | `CoreStrings`、商店页文案 |
| 成本 | 低 |

### F2 · 平台能力与合规可行性 ★

| 项 | 内容 |
|---|---|
| 要回答 | D1 的「后台常驻会话」在 Android / iOS 上到底能不能做，边界在哪？ |
| 必须逐条查证 | ① Android 12+ 前台服务启动限制；② Android 14 `while-in-use` 麦克风权限（后台建 FGS 抛 `SecurityException`）；③ FGS `type=microphone` 声明与「使用中可见」要求；④ Android 后台录音 ~60s 上限；⑤ 电池优化 / Doze 对通知准点的影响；⑥ iOS 后台音频与 Live Activity；⑦ Windows unpackaged 通知能力 |
| 产出 | 能力矩阵（平台 × 能力 × 可行 / 受限 / 不可行 + 规避方案） |
| 落点 | 直接改写 master 第七部分 X-1~X-5，从「定性判断」升级为「有出处的结论」 |
| 成本 | 中 · **决定常驻方向是否成立** |

### F3 · 端侧 ASR 中文数字 / 量词实测 ★

| 项 | 内容 |
|---|---|
| 要回答 | whisper-tiny 对「三十秒」「半分钟」「八组」「20/10×8」这类**关键槽位**识别得准不准？ |
| 为什么关键 | L2 间歇功能的成败全押在这上面；识别不出数字，`Phases` 就永远填不上 |
| 方法 | 构造 50+ 条真实说法 → 录音 → 跑当前管线 → 统计整体 WER **与关键槽位抽取准确率**（数字 / 单位 / 轮次分开算） |
| 产出 | 识别率报告 + 结论：换更大模型 / 走规则补偿 / 两者结合 |
| 前置 | 依赖真实录音（P0-2）；可先用系统录音兜底先测 |
| 落点 | 补充 `open-source-models.md`、`CompositeTimeParser` 容错策略 |
| 成本 | 中 |

## 4. 优先级与建议顺序

| 建议序 | 编号 | 名称 | 杠杆 | 成本 | 依赖 |

| 6 | F1 | 启动方式调研 | 中 | 中 | F2 |
