## 0. 三句话定调

| # | 定调 | 含义 |
|---|---|---|
| 1 | **根 = 待办 / 记录 / 提醒 / 运动** | App 的第一身份是"工具"，占 90% 面积。去掉体贴面，它仍是一个能用的语音待办 + 间歇计时器 |
| 2 | **壳 = 体贴面（一层薄）** | 由用户**自己的记录**喂养出来的体谅。占 10% 面积，可关闭、可清零 |
| 3 | **两个壳 = 两个独立 App** | 有常壳、潮有信壳。同根、异壳、各自独立 |

> 一句话：**我们不做"健康建议"，我们做"替用户记住他自己定过的规矩，并在他需要时说出来"。**

## 1. 什么变了 / 什么没变

| 维度 | V1（旧假设） | V2（本次修正） |
|---|---|---|
| 产品数量 | 一个 App、两种模式 | **两个独立 App**（各自图标 / 名字 / 商店页 / 主色） |

| 输出物 | "今日强度上限"（处方） | **复述 + 一句体谅 + 一个可选动作** |
| 建议来源 | 外部证据库 | **用户自己的记录**（+ 少量常识级种子规则） |
| 文案人格 | 教练 / 同伴 | **懂事的室友**（体贴、不评判、不唠叨、不诊断） |
| 医疗边界 | 尾注免责声明 | **从根上就不是健康建议**，边界天然成立，免责是兜底不是主盾 |

| 核心调研结论 | 睡眠 / 时差 / 周期证据 | ✅ 保留，但**降级为"内部判据"**（决定我们*不说*什么），不再面向用户展示 |

## 2. 根：四个承重功能

这四根是 App 的全部承重结构。体贴面挂在它们上面，不改变它们。

| 根 | 说明 | 与现存产品的关系 |
|---|---|---|
| **待办** | 语音 / 打字建任务，今日聚焦（不做全量计划） | 已有 `VoicePipeline` / MainPage |
| **记录** | 完成即留痕，进日历；可补记、可改名 | 已有 `TimerSession` + CalendarPage 图层 |
| **提醒** | 到期提醒、预提醒；可取消；不做骚扰 | 已有 `Plugin.LocalNotification` |
| **运动** | 间歇计时（语音建会话 → 确认 → 跑 → 留痕） | 已有 TimerPage + RunningTimerHub |

> ⚠️ **运动是四根之一，不是全部。** 拉新话术可以说"带语音的间歇计时器"，但产品定义不是"健身 App"。这是本次最重要的口径修正。

**"体贴面"不算第五根**：它是横切层，挂在"记录"之上——**先有记录，才有体贴**。

## 3. 体贴面：怎么"体贴"而不"咨询"

### 3.1 分界线（这张表是产品的宪法）

| ✅ 我们做的（体贴） | ❌ 我们不做的（健康咨询） |
|---|---|
| 复述你**自己记过**的事 | 判断你的身体**是什么状态** |
| "你昨天记了 23:40 睡" | "你睡眠不足，建议补充…" |
| 说一句体谅的话 | 下结论、给"处方" |
| 给一个**可选**动作，可拒绝 | 给一套**应该**执行的计划 |
| 规则的来源**透明可见**（你写的 / 你改的） | 黑箱算法算出来的 |
| 异常时**只**提示"建议问问医生"，然后停 | 自己往下判断、给方向 |
| 数据存在你手机里 | 上传、分析、画像 |
| 数字是**信息**（"这周偏晚"） | 数字是**评判**（"你退步了"） |

> **一句话判据**：凡是需要"医学训练才能做出"的判断，我们一律不做，改为"提示你去找医生"。

### 3.2 四级阶梯（建议强度逐级上升，每级都可以停）

| 级 | 形态 | 例子 | 风险 | 默认 |
|---|---|---|---|---|
| **L0 复述** | 只把你记过的事说回来 | "昨天记的是 23:40 睡。" | 零 | ✅ 开 |
| **L1 体谅** | 加一句体谅，不催 | "那今天可以慢一点。" | 零 | ✅ 开 |
| **L2 轻建议** | 给一个可选动作，可拒绝 | "要不要把今天换成 20 分钟舒缓？" | 低 | ✅ 开（可关） |
| **L3 就医提示** | 只在异常时出现，不作为 | "这个情况建议问问医生。" | 安全底线 | ✅ 开（不可关） |

**默认最高只到 L1。** L2 需要用户在设置里主动打开（"允许我偶尔提一个小建议"）；L3 只在明确的异常阈值触发，**触发即止**。

> 设计原理：**承认用户比 App 更懂自己的身体**。App 的价值不是"更懂"，而是"更记得"。

### 3.3 "建议"从哪来：把 AI 判断换成**用户自定的规矩**

这是本产品最独特的一层，也是"不构成健康咨询"的**结构性保证**——规则由用户自己写，App 只负责在合适的时机替他想起来。

| 类型 | 来源 | 例子 | 说明 |
|---|---|---|---|
| **种子规则** | 系统预置（常识级，非医学） | "如果昨晚记得很晚 → 今天提示放轻" | 首启时**以建议形式列出**，用户可逐条勾选 / 改文案 |
| **自建规则** | 用户自己写 | "经期第一天我只做拉伸" | 表单形式：`当 [条件] → 我想要 [动作]` |
| **行为习得** | 从历史记录里"看出来"再**问用户** | "你最近三次熬夜后都没练，今天也要放轻吗？" | **只提议、不自动执行**，用户确认后才成为规则 |

规则卡片长这样（**可见、可改、可删**）：

```
当   ① 昨晚入睡晚于平时 1 小时
→    我希望   把今天的安排降一档
      ○ 提醒我   ○ 直接改   ○ 只记着别说
```

**关键**：把"AI 给你建议"换成**"你给自己定过的规矩，我们替你记着"**。这不是咨询，是**替用户记性 + 守约**。责任在用户、工具在 App——法律与伦理边界由此天然划清。

### 3.4 文案人格：懂事的室友，不是教练

| 场景 | ❌ 教练腔 / 评判腔 | ✅ 室友腔 / 体贴腔 |
|---|---|---|
| 熬夜后 | "你的恢复度只有 42%，建议降低强度以避免受伤。" | "昨晚睡得晚。今天想怎么来？" |
| 断了两天 | "Streak Broken! 你已连续中断 2 天。" | "回来啦。想从哪件开始？" |
| 经期第一天 | "检测到经期，已为你切换到黄体期方案。" | "记下了。今天给你留了点余地。" |
| 数据下滑 | "本周完成率 -30%，需要努力。" | "这周偏晚。要不要看看是哪些天？" |
| 异常值 | "疑似 PCOS 风险，建议就医排查。" | "这个变化有点不寻常，建议问问医生。" |

### 3.5 非评判设计原则（联网调研支撑）

| 原则 | 依据 | 落地 |
|---|---|---|
| **不做 streak 羞辱** | 断掉长 streak 会让人"觉得毁了"然后放弃；streak 应是**信息不是身份** | 不用"连续 N 天"做主指标，改用**趋势 / 密度** |
| **漏一天 = 数据，不是失败** | 多条独立来源一致 | 漏了可补记，不留红叉 |
| **标记优先（annotation-first）** | 用户要的是"记下发生了什么"，而非"交出成绩" | 先记录、后解读；解读永远可选 |
| **区间而非刚性目标** | 刚性目标让追踪变成考试 | "半力 / 八折"这类**区间**表达，而非"必须完成 X" |
| **最小版本 / 坏日子版本** | 定义"最小版本"仍算完成 | "今天做 10 分钟舒缓"优于"今天不练" |
| **反馈三要素：即时 / 有意义 / 可行动** | 反馈要能指导下一步 | "你常在周二晚有空 → 要不要把高强度挪到那天？" |
| **优雅暂停，而非退出** | 给 pause 而不是 quit | 提供"暂停一段"开关，不算失败 |
| **欢迎回来，而非你断了** | 文案重构是低成本高回报的留存手段 | 回归语固定为"回来啦"，不做负面提示 |
| **软色不用红叉** | 柔和绿勾优于刺眼红 ❌ | 视觉规范写入设计系统 |
| **本地优先** | 隐私是"体贴"的前提 | 数据端侧、可选、可一键删除 |

### 3.6 与原证据库的关系（内部用，不面向用户）

V1 调研出的睡眠 / 时差 / 周期证据**不废弃**，但角色变了：

- ❌ 不再作为**面向用户的"为什么这么建议"展开内容**（那是"健康科普"，越讲越像咨询）
- ✅ 作为**内部判据**：决定我们**什么时候该停、该说什么、绝不说哪类话**
  - 例：正因为 cycle syncing 无证据（Colenso-Semple 2024），我们**才不按阶段给方案**，只做症状记录与复述
  - 例：正因睡眠 <6h 受伤风险确实上升，我们**才保留一条种子规则**"睡太晚 → 提一句放轻"，但**不说受伤风险数字**

> 一句话：**证据决定边界和口吻，不决定内容。**

## 4. 两个壳：同根异壳

|  | 有常壳 | 潮有信壳 |
|---|---|---|
| **名字含义** | 《礼记》「起居有常」 | 李益《江南曲》「早知潮有信」 |
| **管什么时间** | **外面的时间**（exogenous） | **里面的时间**（endogenous） |
| **输入** | 作息、睡眠、日程、出行、时区 | 周期日期、症状、经量、情绪（**均为用户自填**） |
| **体贴面** | **日程管家式的体谅**："懂你忙" | **同伴式的体谅**："懂你不舒服" |
| **种子规则** | 睡眠 / 出行相关几条 | 身体感受相关几条 |
| **主色气质** | 沉稳、秩序（墨蓝 / 晨白） | 柔和、潮汐（薄暮 / 水色） |
| **目标人群** | 生活节奏被日程 / 出差打乱的人 | 希望把周期纳入生活安排的女性 |
| **一句话** | "今天能到什么程度？" | "今天想怎么来？" |

**两壳相同的东西（= 根）**：待办、记录、提醒、运动四个功能，以及整套语音交互、计时引擎、留痕日历、隐私口径。

**两壳不同的东西（= 壳）**：名字、图标、主色、输入字段、种子规则、文案人格、商店定位。

## 5. 有常壳 · 体贴设计

### 5.1 承重与体贴的分工

| 层 | 内容 |
|---|---|
| **根** | 语音待办（"今晚要加班"）、运动计时、留痕 |
| **体贴面** | 睡眠 / 日程 / 出行 → 复述 + 体谅 + 可选动作 |

### 5.2 交互示例

```
[早晨打开]
  昨晚记的是 23:40 睡，比平时晚 1 小时。
  今天不用太满。
  ▸ 要不要把今天安排成轻松档？（改 / 不改）

[记录"明天早班机"后]
  记下了：明天早班机。
  那今天适合把重的那项挪到后天。
  ▸ 移到周四（改 / 保持）

[出差回来后]
  回来啦。跨了 3 个时区，头几天不用急着上强度。
  ▸ 帮我排一下这几天（看 / 不用）
```

### 5.3 种子规则（降级后的表述）

> 原型来自 V1 证据库，但**表述全部改写为"体贴提示"**，不再是"处方"。

| # | 触发（用户自己的记录） | 体贴提示（默认 L1 / L2） |
|---|---|---|
| A1 | 昨晚睡得比平时晚很多 | 今天可以轻一点 |
| A2 | 记录里连着几天短睡 | 这几天要不要都留点余地 |
| A3 | 通宵 / 几乎没睡 | 今天更适合当休息日 |
| A4 | 记录了即将出行 | 出发前这几天降一档 |
| A5 | 跨时区出行回来 | 头几天不用急着上强度 |
| A6 | 东行（往东飞）回来 | 早上别太早起，下午傍晚更舒服 |
| A7 | 日程里有空档 | 想上强度的话，下午到傍晚是个好窗口 |
| A8 | 一次普通飞行 | 也算一天"在路上"，别排太满 |

**全部可关、可改、可删。** 关掉后 App 退化成一个纯粹的语音待办 + 计时器。

## 6. 潮有信壳 · 体贴设计

### 6.1 承重与体贴的分工

| 层 | 内容 |
|---|---|
| **根** | 语音待办、经期 / 身体感受**记录**、运动计时、留痕 |
| **体贴面** | 记录 → 复述 + 体谅 + 换形态（不取消） |

### 6.2 ⚠️ 立场（沿用 V1，且因本次定位而更稳）

> **不做 cycle syncing（激素决定论）**；只做**症状记录 + 症状驱动的体贴**。

依据（内部判据）：Colenso-Semple et al. 2024, *J Physiol*（周期阶段**不影响**肌肉蛋白合成）；2023 系统伞形综述（不影响肌力 / 适应 / 肥大）；2024 / 2025 综述（**应由症状而非激素波动指导训练**）；2020 meta（经期或有轻微下降，幅度小不普遍）；仅约 **12%** 女性为标准 28 天周期。

**正因定位是"待办 / 记录"而非"健康"，这个立场反而更好守**——我们根本不宣称"科学训练方案"，只宣称"我替你记着你说过的那几天"。

### 6.3 交互示例

```
[记录"今天第 1 天，肚子疼"]
  记下了：第 1 天，肚子疼。
  今天不一定要练，也可以就去走走、拉一拉。
  ▸ 给我一个 10 分钟舒缓（要 / 不用）

[记录"今天状态很好"]
  记下了：今天状态好。
  ▸ 那今天可以正常来（看看安排）

[周期第 40 天仍无记录]
  你的周期记录有点不太寻常。
  这种情况建议问问医生。（本 App 不做判断）
```

### 6.4 种子规则（降级后的表述）

| # | 触发（用户自填） | 体贴提示 |
|---|---|---|
| B1 | 记了"疼" | 今天可以换成舒缓 / 拉伸，不一定取消 |
| B2 | 周期第 1–7 天 | 允许自己轻一点，**但不强制** |
| B3 | 记了"累 / 情绪低" | 今天减量不减习惯 |
| B4 | 身体不适 + 睡眠差叠加 | 取更轻的那个建议 |
| B5 | 周期异常（记 <24 天 / >35 天 / 长时间无记录） | **只说"建议问问医生"** |
| B6 | 记了"今天很好" | 允许上调——体贴不只是做减法 |

### 6.5 隐私（体贴的前提）

- 生理数据**端侧存储**、**默认不上传**、**可一键删除**
- 记录项**可空**：用户不想填就不填，不设必填
- 与另一壳**不打通**（若两壳都装，数据不互通）——这是隐私承诺的一部分

## 7. 两壳关系（工程实现层面）

**用户视角**：两个独立 App，各自完整，只装一个也能用。

**工程视角**（供后续选型，非本次实现）：

| 方案 | 描述 | 优劣 |
|---|---|---|
| P1 | **同一仓库，两个启动项目**（`YouChang.App` / `Chaoyouxin.App`），共用 `VoiceTodo.Core` + 共享 UI 库 | 复用最高、成本最低；需处理"两套图标 / 名字 / 主色"的构建配置 |
| P2 | 一个 App + 编译开关（同一份代码出两个包） | 复用最高，但"体贴面"混在一个 UI 工程里，易互相污染 |
| P3 | 两个独立仓库 | 隔离最干净，但四个根功能要写两遍 |

**倾向 P1**：根（语音 / 计时 / 留痕 / 待办）是重资产，必须复用；壳（名字 / 图标 / 主色 / 规则 / 文案）是薄配置，用构建变体或 DI 注入区分。

> 注：现存工程已具备条件——`VoiceTodo.Core` 零依赖、平台选择点唯一（`MauiProgram.CreateMauiApp()`），把"壳"抽成一层配置注入即可，**不需要动根**。
